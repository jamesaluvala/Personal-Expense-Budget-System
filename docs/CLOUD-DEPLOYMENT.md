# Cloud deployment - no local application installation

This guide builds and runs the application on a hosting provider, not on your Mac. Your browser is used for GitHub, Railway and optionally Vercel. You may extract the ZIP in Finder without installing or running the application.

**There is no live URL yet.** You must supply accounts, authorize your own repository, provision MySQL and complete a successful deployment. Hosting, database storage, CI usage or backups may incur charges. Check current plans and spending limits before creating services. Nothing in this package purchases a plan for you.

## Recommended route: one Railway app and one MySQL service

A single app serves both React and Java. This avoids a separate frontend proxy until the full system works.

### A. Put the source in a private GitHub repository

1. Extract `Personal-Expense-Budget-System.zip` using Finder. Open its inner project folder.
2. In GitHub's website, create a new private repository, for example `personal-expense-budget`.
3. Use **Add file > Upload files** to upload the extracted project contents. Do not upload only the ZIP. `Dockerfile`, `backend` and `frontend` must be at the repository root, not inside an extra wrapper directory.
4. Include hidden `.github`, `.gitignore` and `.dockerignore` files. Finder's Command+Shift+Period toggles hidden files. Use separate small upload batches when necessary.
5. Commit the files. Open the repository's Actions tab and inspect the verification workflow. A green result must come from an actual run, not the source package's presence. Workflow failures should be fixed before your demonstration.

GitHub stores source. It does not by itself create the MySQL service or a running Java website. No real password, `.env` file or database export should be uploaded.

### B. Provision MySQL

1. Create a Railway project in its web dashboard. Add the MySQL database template/service and keep it in the same project/environment as the application.
2. Confirm that the database has persistent storage mounted at `/var/lib/mysql`. Do not remove this volume when redeploying the app.
3. Keep database access private. The Spring Boot service needs private networking, not a public MySQL URL.
4. Keep generated database passwords secret. Enable an appropriate backup policy and verify a restore before storing important records.

### C. Create the application service

1. Add a service from the GitHub repository in the same Railway project. Grant only the repository access that is needed.
2. Use the repository root as the build root. Railway should detect the root `Dockerfile`; select Dockerfile building if the dashboard asks. Leave custom build/start commands empty so the Dockerfile's ENTRYPOINT is used.
3. Use a single application replica. Set health-check path to `/api/health` in the service settings. This endpoint also checks database connectivity.
4. Add the following application service variables. The examples assume the database service is named **MySQL**. Change that part to the exact service name displayed in your project.

| Variable | Value |
|---|---|
| DB_URL | `jdbc:mysql://${{MySQL.MYSQLHOST}}:${{MySQL.MYSQLPORT}}/${{MySQL.MYSQLDATABASE}}?sslMode=REQUIRED&connectionTimeZone=UTC` |
| DB_USER | `${{MySQL.MYSQLUSER}}` |
| DB_PASSWORD | `${{MySQL.MYSQLPASSWORD}}` |
| COOKIE_SECURE | `true` |
| APP_CURRENCY | `INR` |
| APP_TIME_ZONE | `Asia/Kolkata` |

Railway's reference-variable picker can insert the database values instead of manually typing reference syntax. `DB_URL` must begin `jdbc:mysql://`, not `mysql://`. The sample requires TLS. If your database template does not support TLS, configure TLS or use a TLS-capable MySQL service; do not silently disable encryption for a public database connection. For stronger production certificate verification, use the provider's verified CA/hostname configuration.

Keep `PORT` as the platform-provided port unless the provider explicitly requires a manual value; the app reads it. Do not put any `DB_*` values in Vercel frontend variables.

5. Deploy. The Dockerfile downloads dependencies, runs frontend utility tests, builds React, runs the Java/H2 test suite and packages Java with the React output. A failing build stops deployment; the test suite has not already been proven in this ZIP.
6. On success, generate a public HTTPS domain in application networking settings. Open `/api/health` on that domain, then open the root website. The root must show the sign-in page.
7. Register a new account. The records should start empty. Complete `DEMO-CHECKLIST.md` and restart only the application service to verify persistence.

The URL generated by Railway is a full application URL. You can demonstrate it directly. Initial cloud builds need internet access and can take several minutes.

No legacy `railway.toml` or `railway.json` is required. Configure the current service settings in the dashboard; provider interfaces change over time.

## Optional: put the React frontend on Vercel

Do this after the Railway application works, keeping Java/MySQL running there.

1. Edit the exact file **`frontend/vercel.json`** in GitHub. Replace only `https://replace-me.up.railway.app` with the real HTTPS domain of your Railway application. Keep the `/api/:path*` suffix. This changes the API destination; it does not create a backend or move the database.
2. In Vercel, import the same repository. Set **Root Directory: `frontend`**, framework **Vite**, install command **`npm install`**, build command **`npm run build`**, output **`dist`**, Node **22.x**.
3. Deploy and open the generated HTTPS URL. There is no `VITE_API_URL` requirement; calls use `/api` and the rewrite forwards them to Java.
4. Repeat registration/login, create/edit/delete and CSV checks on the Vercel URL. In browser network tools, `/api/auth/csrf` must return JSON, and API responses must be `Cache-Control: no-store`. Confirm the HttpOnly session cookie remains attached to subsequent requests.
5. Treat Railway and Vercel as separate browser login origins. Sign in again on the Vercel domain; users/records remain in the same MySQL database.

Do not add wildcard CORS, disable CSRF, expose SQL credentials to React, or replace APIs with localStorage just to make a frontend-only deployment appear to work.

## Troubleshooting

| Symptom | What to check |
|---|---|
| Build cannot find Dockerfile | Repository root contains the extracted source, not a ZIP or extra folder |
| Backend connection page in React | Java deployment health and the exact destination in `frontend/vercel.json` |
| API returns HTML / 404 | Vercel root is `frontend`, rewrite starts `/api`, backend domain is correct |
| Cannot connect to MySQL | Private host/port, same Railway environment, service name in references, DB password and TLS |
| Login succeeds then acts signed out | HTTPS, Secure cookie, Set-Cookie forwarding, single replica and no cached API responses |
| HTTP 403 on a write | Fetch fresh CSRF token with the same cookie/session; do not disable the filter |
| HTTP 429 | Basic demo rate limit; wait for its 15-minute window instead of repeatedly retrying |
| Flyway checksum error | Restore the applied migration file and add a new migration; do not reset/delete the data volume |
| Out-of-memory build/runtime | Inspect the provider logs and allocated resources; review cost before increasing resources |

If a build or test fails, keep the exact error output, redact credentials, and fix it before declaring the project complete. Do not publish actual financial data until backups and full testing are verified.
